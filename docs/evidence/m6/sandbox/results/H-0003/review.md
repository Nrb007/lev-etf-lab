There is no shift(-k), no whole-series statistic and no centered window. Whether the position is applied the next day is the engine's job, and the leakage test passes.

The spec itself calls the hypothesis pure noise, so most of the grid is unjustified. The best of 56 noise points will look good by selection alone, and the multiple-testing correction must be applied in full.
- Mechanism: the yaml `mechanism` field names a flow effect around month boundaries. The grid does not match it. A start_day of 8-24 with a short length is a mid-month window, not a turn of month. The file name and title ("turn_of_month") also disagree with the signal, which works on calendar day of month and not on trading days before or after month end. The mechanism is weak and does not explain the grid. The spec does admit it expects a failure.
- Signal semantics: windows do not wrap past month end. For example, start_day 28 with length 24 covers only days 28 to 31 (3 or 4 days). Many grid points are therefore duplicates or near-duplicates of each other (for example start_day 28 at any length >= 4). The effective number of distinct strategies is below 56, but N is still counted as 56.

That is acceptable for the mechanism, but cost realism depends on the engine cost config, which I did not review. Short windows are in cash most of the time, so Sharpe could be inflated by low volatility exposure.

## Post-run review - H-0003 - 2026-09-30T23:30:51Z

Findings:
- Verdict: results/H-0003/verdict.json has `train_verdict: reject` with reasons dsr, permutation, sensitivity, stress and regime. The verdict matches the metrics, and the hypothesis should not advance to hold-out consideration. The spec (H-0003_turn_of_month.yaml lines 6-8) predicted this outcome.
- Limit of this review: I could not filter ledger/trials.jsonl for H-0003. Bash is limited to pytest and leakage, and the file is too large to Read whole. I read only the first 3 rows, which are H-0001 trials. I did not check the H-0003 trials individually (time in market, turnover, cost). Everything below comes from verdict.json.
- Trial count: `n_trials` is 224 (dsr and spa details), but the spec grid has 56 points. The chosen trial is H-0003-000119, so there are more than 56 H-0003 trials. The sensitivity neighbors (`tests.sensitivity.details.neighbors`) use lengths 14, 19, 29 and 34, none of which are in the spec grid, and that explains part of the excess. The spec under-states its real search size. Someone should confirm where 224 comes from (perturbation runs, re-runs, or a ledger-wide count).
- Edge of grid: `chosen_params` is length 24, which is the maximum of the spec's length values. The best neighbor (length 34, Sharpe 1.22) is larger still, and Sharpe rises with length (14: 0.75, 19: 0.96, 24: 1.13, 29: 1.15, 34: 1.22). The best result is a monotonic drift toward "hold almost all month", which is buy-and-hold in disguise and not a calendar effect.
- Benchmark: `sensitivity.details.benchmark_sharpe` is 1.2217 and the base Sharpe is 1.1322, so the strategy is below buy-and-hold. `fraction_beating_benchmark` is 0.0 against a threshold of 0.8. There is no edge here.
- Permutation: `tests.permutation` p=0.235 (threshold 0.05), observed Sharpe 1.13 against a null mean of 1.06 and a p95 of 1.21. A random shift of the same window gives almost the same Sharpe, so the result is market exposure and not timing.
- DSR: `tests.dsr.value` is about 7e-25 (threshold 0.95). The per-period Sharpe 0.071 is far below the expected max Sharpe of 0.242 from 224 trials.
- Regime: `tests.regime.partitions` shows total excess of -1.83 in both partitions, 0 of 3 VIX terciles positive, and 7 of 15 years positive (2011, 2019 and 2020 at roughly -1.0 each). `max_single_regime_share` is null, presumably because total excess is negative, so the concentration check was not evaluated. The fail is correct, but the null means the test did not measure concentration.
- Stress: `tests.stress.value` is -0.126 at 3x cost and a 200 bps financing spread (threshold 0.0). The strategy loses money under stress.
- Display inconsistency in verdict.json: `tests.sensitivity.value` is 0.93 against a threshold of 0.6 but `pass` is false, because the pass rule uses `fraction_beating_benchmark` (0.0 against 0.8). A reader who compares `value` with `threshold` would think it passed. The `regime` test has the same pattern (value 0.0, threshold 0.6, pass false, which is consistent, but the `value` field there is not the same quantity as in other tests). This is worth a note in the judge output for readers.
- PBO and SPA pass: `pbo` is 0.0 (pass) and `spa` p=0.02 (pass), which contradict the dsr, permutation and regime results. PBO of 0.0 with mean logit about 3.98 means the in-sample best stays best out of sample, which is expected when all 224 trials are nearly the same long-biased exposure with one common market return. PBO is uninformative for a family that is not diverse. SPA p=0.02 is probably detecting positive drift of the underlying (a simulated demo world with positive drift), not calendar skill, and it is not a point in this hypothesis's favour. Neither pass should be used as support.
- Sharpe level: base Sharpe 1.13 looks high only because TQQQ (simulated) has a high Sharpe itself. Buy-and-hold is 1.22. No implausible result to flag.
- Universe: the ledger rows I read carry `research_universe: real` (H-0001 rows), and H-0003 also declares `real` with demo notes (carried over from the pre-run review). Since the run is on the simulated universe (as the task states), none of these numbers say anything about real markets.
